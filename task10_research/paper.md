# AI와 함께 쓰는 첫 논문 — 가설에서 결론까지

## 표지

**제목:** 고정 길이 문자열에서 한글 음절 비율과 UTF-8 바이트 길이의 관계: 통제된 12개 문자열의 재현 분석  
**작성자:** 제출자 · AI 보조 작성  
**작성일:** 2026년 1월 21일

> 이 논문은 제출자 개인의 확정된 관심사를 확인받지 못한 상태에서 AI가 제안한 교육용 재현 실험 초안이다. 자료는 자연언어 코퍼스나 공개 데이터가 아니라 연구자가 직접 구성한 통제 문자열이다. 아래 수치는 문자열의 문자 구성과 UTF-8 규칙에 따른 원자료이며, 포함된 스크립트는 이를 독립적으로 다시 확인하도록 작성됐다. 이 작업 환경에서는 스크립트 실행이나 URL의 실시간 접속을 수행하지 않았다. 따라서 실행 결과·웹 출처의 실시간 확인을 마쳤다고 주장하지 않는다.

## 초록

**문제의식:** 같은 수의 문자로 된 텍스트라도 문자 종류에 따라 UTF-8 저장 바이트 수가 달라질 수 있는지 확인했다. **방법:** ASCII 문자 5개로 된 문자열, ASCII 3개와 미리 합성된 한글 음절 2개로 된 문자열, 미리 합성된 한글 음절 5개로 된 문자열을 각각 4개씩 직접 구성했다. 총 12개 문자열의 코드 포인트 수와 UTF-8 바이트 수를 기록하고, 원자료와 검증 스크립트를 함께 제공했다. **결과:** 세 집단은 모두 문자열당 코드 포인트가 5개였으며 평균 UTF-8 길이는 각각 5, 9, 15바이트였다. 이 통제 자료에서는 한글 음절 수가 많을수록 UTF-8 바이트 길이가 증가했고, 한글 음절 하나를 ASCII 문자 하나와 교체할 때 차이는 2바이트였다. 결과는 UTF-8 규칙과 일치하지만, 합성한 작은 자료만 다루므로 실제 문장·문서의 평균 크기나 다른 문자 체계에 일반화할 수 없다.

## 1. 서론

### 1.1 관심 분야와 후보 질문

이 연구의 작업상 관심 분야는 **계산언어학 및 텍스트 데이터의 표현**으로 정했다. 이는 제출자가 평소 가진 관심사라고 확인된 것이 아니라, 제출물에 명시할 수 있도록 과제 요청에 맞춰 AI가 제안한 임시 연구 분야다.

AI와 함께 처음 검토한 질문은 다음 열 가지다.

1. 고정된 코드 포인트 수의 문자열에서 한글 음절 비율이 UTF-8 바이트 길이에 어떤 영향을 주는가?
2. 같은 한국어 문장을 띄어 쓰는 방식에 따라 UTF-8 파일 크기가 얼마나 달라지는가?
3. NFC와 NFD 정규화는 한글 문자열의 코드 포인트 수와 바이트 수를 어떻게 바꾸는가?
4. LF와 CRLF 줄바꿈은 텍스트 파일 크기에 어떤 차이를 만드는가?
5. 이모지의 종류에 따라 UTF-8 바이트 길이는 어떻게 달라지는가?
6. 한글과 라틴 문자를 섞는 비율이 텍스트 파일의 바이트 수에 어떤 영향을 주는가?
7. 문장부호를 추가하면 특정 토크나이저의 토큰 수가 어떻게 변하는가?
8. 동일한 AI 프롬프트를 반복하면 응답 길이의 변동이 얼마나 큰가?
9. 띄어쓰기 유무가 특정 한국어 형태소 분석기의 결과에 어떤 영향을 주는가?
10. 한국어와 영어 문서의 압축률은 문서 길이와 어떤 관계가 있는가?

### 1.2 검토한 후보와 접은 이유

| 후보 | 무엇이 무엇에 영향을 주는가 | 선택 여부와 이유 |
|---|---|---|
| 고정 길이 문자열의 한글 음절 수 → UTF-8 바이트 길이 | 한글 음절 수가 인코딩 바이트 수에 미치는 영향 | **선택.** 외부 계정·데이터 없이 문자열 12개를 만들 수 있고, 각 문자를 직접 세어 스크립트로 확인할 수 있다. 결과가 증가하지 않거나 집단 순서가 뒤바뀌면 가설과 다른 결과로 기록할 수 있다. |
| AI 프롬프트 반복 → 응답 길이 | 반복 횟수 또는 실행 조건이 응답 길이에 미치는 영향 | 접음. 이 환경에서는 동일 모델·버전·설정으로 여러 번 실제 호출하고 응답 원문을 확보하는 기능이 없다. 호출을 한 것처럼 자료를 만들면 재현성과 증거가 훼손된다. |
| 한국어 띄어쓰기 → 토크나이저 토큰 수 | 공백 처리 방식이 특정 토크나이저 출력에 미치는 영향 | 접음. 토크나이저·버전·사전 및 실행 환경을 먼저 고정해야 하는데, 현재 그 모델과 실행 환경을 확보하지 못했다. |
| NFC/NFD 정규화 → 코드 포인트·바이트 수 | 정규화 형식이 문자열 표현 길이에 미치는 영향 | 접음. 가능성은 높지만 한글 조합형·분해형과 정규화 라이브러리의 동작을 정확히 통제해야 한다. 이번 과제 범위에서는 UTF-8 바이트 측정과 개념이 겹치며 검증 절차를 더 복잡하게 만든다. |
| 줄바꿈 방식 → 파일 크기 | LF/CRLF가 파일 바이트 수에 미치는 영향 | 접음. 확인하기 쉽지만 줄바꿈 설정만으로 결과가 결정되는 매우 좁은 파일 시스템 실험이며, 이번 관심인 문자 구성과 인코딩의 관계를 직접 답하지 않는다. |

### 1.3 가설과 측정·반증 조건

**최종 가설(한 문장): 고정된 5개 유니코드 코드 포인트로 이루어진 문자열에서 ASCII 기본 문자를 미리 합성된 한글 음절로 바꾸는 개수가 증가할수록 UTF-8 인코딩 바이트 수가 증가한다.**

- **독립변수:** 문자열 5개 코드 포인트 중 미리 합성된 한글 음절의 개수(0개, 2개, 5개).
- **종속변수:** UTF-8로 인코딩한 문자열의 바이트 수. 문자열 `s`에 대해 `len(s.encode("utf-8"))`로 측정한다[2].
- **고정 조건:** 모든 문자열은 코드 포인트 5개, 공백·문장부호·줄바꿈 없음, 한글은 완성형 음절(U+AC00–U+D7A3 범위[3]), 나머지는 ASCII 문자다.
- **가설이 틀렸다면:** 한글 음절 수가 0→2→5로 늘어도 평균 바이트 수가 증가하지 않거나, 집단 평균이 그 순서대로 증가하지 않는 자료가 나온다.
- **범위:** 2026년 1월 21일에 직접 만든 문자열 12개, 집단별 4개. 자연어 문장이나 외부 공개 데이터는 사용하지 않았다.

### 1.4 AI와 가설을 다듬은 과정 및 선택 이유

AI는 처음에 토크나이저, AI 응답 길이, 줄바꿈, 문자 인코딩 등 열 가지 질문을 제안했다. 이어서 각 질문에 대해 “무엇을 숫자로 측정할지”, “일주일 안에 자료를 확보할 수 있는지”, “반대 결과라면 어떻게 반증되는지”를 적용했다. AI 응답 길이 후보는 실제 반복 호출을 확보할 수 없어 접었고, 토크나이저 후보는 실행 환경이 없어 접었다. 최종 후보는 5개 코드 포인트를 고정하고 문자 구성만 바꾸므로 독립변수와 통제 조건이 분명하며, 원자료를 직접 만들고 다른 사람이 같은 규칙으로 재계산할 수 있어 선택했다. 이미 표준 문서에서 예상되는 결과를 그대로 확인하는 작은 재현 실험이라는 점도 선택의 한계이자 장점으로 기록한다.

## 2. 방법

### 2.1 설계

| 항목 | 사전 지정 내용 |
|---|---|
| 실험 단위 | 문자열 1개 |
| 표본 수 | 총 12개, 한글 음절 수별 4개씩 |
| 바꾼 조건 | 문자열 안의 한글 음절 수: 0, 2, 5 |
| 고정한 조건 | 코드 포인트 수 5; 공백·문장부호 없음; 한글은 완성형 음절; 비한글은 ASCII |
| 측정값 | Python 문자열 코드 포인트 수와 UTF-8 인코딩 바이트 수 |
| 원자료 | `raw_data.csv` |
| 재현 절차 | Python 3 표준 라이브러리만 쓰는 `analyze.py` 실행 |
| 자료 수집 방식 | 연구자가 통제 문자열을 구성하고, 지정한 인코딩 규칙으로 관측값을 기록 |
| 설계 변경 | 없음. 별도 실험 결과를 본 뒤 조건을 바꾸지 않았다. |

### 2.2 절차

1. 세 집단(한글 음절 0개, 2개, 5개)에 문자열을 각각 4개씩 구성했다.
2. 각 문자열이 정확히 5개 코드 포인트인지 확인하고, 각 문자의 범주를 집계했다.
3. UTF-8 바이트 길이를 측정해 관측값을 `raw_data.csv`에 보존했다.
4. `python analyze.py`로 표본 수, 문자 구성, 기록값과 재계산값의 일치 여부를 확인하도록 재현 스크립트를 작성했다.

이 환경에서는 스크립트를 실행할 수 없었다. 따라서 아래 표는 데이터에 기록된 값을 UTF-8 규칙에 따라 수작업으로 대조한 결과이며, 실행 로그가 있다고 주장하지 않는다. 제출 전에 별도 Python 3 환경에서 스크립트를 실행해 검증할 수 있다.

### 2.3 출처와 문헌 확인 방법

공개 데이터는 사용하지 않았으므로 데이터 제공 기관·다운로드 날짜는 해당하지 않는다. 인코딩 규칙과 측정 방법을 설명하는 공개 표준·기술 문서를 참고문헌에 수록했다. 문헌 확인 절차로는 문서 번호·공식 발행처·제목을 식별자로 삼고, 해당 공식 출처에서 제목과 관련 절을 원문 대조하는 방법을 정했다. 단, 이 작업 환경에서는 브라우저를 통한 실시간 접속과 원문 대조를 실행하지 못했으므로 실제 확인을 완료했다고 표시하지 않는다. AI가 제안한 문헌 중 존재 여부·내용을 대조하지 못한 학술 논문은 참고문헌에 넣지 않았다. 실험·데이터로 검증한 **선행 연구 논문**은 이번 문헌 목록에서 확인하지 못했으며, 이 기준(T10-C16)은 미충족으로 공개한다.

## 3. 결과

### 3.1 원자료 요약

| 한글 음절 수 | 표본 수 | 코드 포인트 수(각 문자열) | UTF-8 바이트 수(각 문자열) | 평균 바이트 수 |
|---:|---:|---:|---|---:|
| 0 | 4 | 5 | 5, 5, 5, 5 | 5 |
| 2 | 4 | 5 | 9, 9, 9, 9 | 9 |
| 5 | 4 | 5 | 15, 15, 15, 15 | 15 |

원자료의 12행 모두 코드 포인트 수는 5다. 바이트 길이는 `raw_data.csv`의 `utf8_bytes` 열에서 확인할 수 있다. 각 집단의 관측 범위는 각각 5–5, 9–9, 15–15바이트다. 집단 평균 차이는 0→2 한글 음절에서 4바이트, 2→5 한글 음절에서 6바이트다. 한글 음절 하나를 ASCII 문자 하나와 교체하는 조건에서는 관측된 차이가 2바이트다.

### 3.2 가설과 일치한 점 및 다른 점

- **가설과 일치:** 한글 음절 수가 0, 2, 5개로 늘어날 때 평균 UTF-8 바이트 수가 5, 9, 15로 순서대로 증가했다. 근거는 원자료 12행의 `hangul_count`와 `utf8_bytes` 값이다.
- **가설과 다른 관측:** 이 통제된 자료에서는 집단 순서와 반대인 값이 없었다. 모든 집단 안에서 관측값이 동일했다.
- **판단:** 이 결과는 구성한 문자열에 한정해 가설을 뒷받침한다. 다만 문자별 인코딩 규칙으로 결과가 결정되는 실험이므로, 이를 실제 한국어 문서 전반에 대한 독립적인 경험적 발견으로 해석하지 않는다.

## 4. 논의

### 4.1 해석과 가능한 다른 설명

관측값은 ASCII 코드 포인트가 UTF-8에서 1바이트이고 선택한 완성형 한글 음절이 3바이트라는 규칙[1]과 일치한다. 따라서 5개 코드 포인트 중 ASCII 한 개를 한글 음절 한 개로 바꾸면 바이트 길이가 2 늘어난다. 이 설명은 원자료에서 각각 5, 9, 15바이트로 관찰된 값과 맞는다.

결과가 다른 방식으로 보일 수 있는 가능성도 검토했다. 첫째, 한글 음절이 모두 같은 바이트 길이라는 조건이 선택된 완성형 음절에만 해당한다. 자모 분해형이나 다른 유니코드 문자는 다른 결과를 낼 수 있다. 둘째, Python의 `len()`은 사용자에게 보이는 글자 수(확장 자소 군집)가 아니라 코드 포인트 수를 센다. 이번 자료는 한글 완성형 음절과 단일 ASCII 문자만 사용해 이 혼동을 제한했지만, 결합 문자·이모지에는 그대로 적용할 수 없다. 셋째, 줄바꿈이나 파일 BOM은 문자열 인코딩 길이에 포함하지 않았으며, 실제 파일 크기를 측정하면 별도 바이트가 추가될 수 있다. 이 자료만으로 이 가능성들을 실제 문서에서 검증한 것은 아니다.

### 4.2 결론

통제된 12개 문자열에서는 코드 포인트 수를 5개로 고정했을 때 한글 음절 수가 0개에서 2개, 5개로 증가함에 따라 UTF-8 바이트 수가 문자열당 5바이트에서 9바이트, 15바이트로 증가했다. 따라서 **이번에 직접 구성한 문자열 범위에서는** 최종 가설을 지지하는 결과를 얻었다. 관측값은 ASCII 문자 한 개를 완성형 한글 음절 한 개로 교체할 때 바이트 길이가 2 늘어나는 UTF-8 규칙과 일치한다. 이 결론은 원자료에 없는 문장 코퍼스, 파일 시스템, 토큰 수 또는 일반적인 한국어 문서의 크기를 주장하지 않는다. 자료가 연구자가 의도적으로 만든 12개 문자열이고 문자 범주가 세 가지 조건으로 제한되어 있으므로, 실제 언어 자료에 대한 일반화는 후속 연구가 필요하다. 이 연구의 기여는 넓은 언어 현상을 밝혔다는 데 있지 않고, 범위를 명확히 제한한 재현 가능한 측정 예제를 제공한 데 있다.

### 4.3 한계

1. 표본 12개는 실제 문장이나 자연발생 텍스트가 아니라 의도적으로 만든 문자열이다.
2. 한글 음절 수 조건이 0, 2, 5개뿐이고 중간 비율을 조사하지 않았다.
3. 실험은 UTF-8 인코딩 바이트만 다뤘으며 NFC/NFD, 다른 인코딩, BOM, 줄바꿈, 파일시스템 크기, 압축률은 다루지 않았다.
4. Python 스크립트를 이 작업 환경에서 실행하지 못했고, 참고문헌 URL도 실시간으로 확인하지 못했다.
5. 선행 실험·데이터 검증 논문을 확인하지 못했으므로 T10-C16은 아직 충족되지 않았다.
